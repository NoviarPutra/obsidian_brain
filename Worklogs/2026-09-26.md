### [01:05] Hardening `core/error_relay.py`

Tujuh titik, semua di satu file (+148/−29 pada iterasi ini):

1. **Threshold konflik** — `Conflict` di-log warning; paging hanya bila
   `CONFLICT_ALERT_THRESHOLD=3` dalam `CONFLICT_ALERT_WINDOW_S=120`s, pesan
   `Persistent getUpdates Conflict`, counter reset setelah paging.
2. **Sengaja `Conflict`-only** — `NetworkError` tidak bisa dipakai sebagai grup karena `BadRequest`
   mewarisinya. Diverifikasi pada PTB 22.8 di image: `BadRequest -> ['NetworkError', ...]`. Menyaring
   `NetworkError` akan menelan bug asli.
3. **Cooldown per-error** — satu alert per signature `type:message` per `ALERT_COOLDOWN_S=300`s, jadi
   handler yang stuck di retry loop mengirim 1 DM bukan 500. Timestamp tidak di-refresh saat ditekan,
   sehingga kerusakan permanen tetap mengabari owner sekali per window, bukan hening total.
4. **Anti memory leak** — seluruh state berbatas: `_conflict_hits` = `deque(maxlen=3)`, `_last_alert`
   = `OrderedDict` dengan `ALERT_CACHE_MAX=64` + pemangkasan berbasis waktu. Error string unik (yang
   membawa id/timestamp) tidak lagi bisa menumbuhkan dict tanpa batas. Basis waktu `time.monotonic()`,
   imun lompatan wall-clock/NTP.
5. **Alert selalu muat 4096 char** — budget diturunkan dari `_ALERT_OVERHEAD` (panjang template
   kosong, jadi ikut otomatis bila template diedit): error 400, update 900, sisanya traceback yang
   dipotong dari kepala karena ekor berisi kegagalan sebenarnya. Sebelumnya `err_str` tak dibatasi
   sama sekali sehingga pesan bisa ditolak API.
6. **Entity-safe clipping** — potongan teks ter-escape bisa jatuh di tengah entity HTML (`&quo`) yang
   ditolak Telegram sebagai HTML malformed; fragmen menggantung dibuang regex.
7. **Handler tidak bisa melempar** — `to_dict()`/`json.dumps` hostile ditangkap, render gagal jatuh ke
   alert minimal, penolakan HTML jatuh ke plain-text sekali, `bot`/`ADMIN_USER_ID` kosong ditangani
   eksplisit. Error handler adalah lini terakhir; exception di dalamnya tidak punya tujuan.

**Regression test** `tests/test_conflict_alert.py` — 12 check, plain asserts tanpa framework, urut
definisi supaya gejala yang dilaporkan jadi yang pertama merah. Dijalankan di container throwaway
(`--network none`, `PYTHONDONTWRITEBYTECODE=1`) agar tidak menyentuh bot produksi:

```bash
docker run --rm --network none -v /home/voldemort/services/telegram-bot:/app -w /app \
  -e PYTHONPATH=/app/src -e PYTHONDONTWRITEBYTECODE=1 \
  --entrypoint python voldemort-menu-bot:2.9.4 tests/test_conflict_alert.py
```

Terhadap relay di `git HEAD` → RED pada `test_transient_conflict_is_quiet`, mereproduksi teks alert
asli persis termasuk `Update Context: "None"`. Terhadap relay hardened → `PASS: 12 checks`.

Cakupan: transient quiet, flap pages once + reset, slow-drip 6 konflik lintas window tidak pernah
paging, exception nyata tetap paging, retry loop 50× → 1 DM, cooldown expiry paging lagi, cache
berbatas di bawah 320 error unik, benign list utuh, alert oversized tetap ≤4096 dengan entity HTML
valid, update tak-serializable tidak mematikan handler, penolakan HTML jatuh ke plain text,
`bot`/admin kosong survivable.

### [01:21] Lapis kedua: `core/singleton.py` — cegah konflik, bukan cuma jangan memaging

Patch relay hanya menghentikan *paging*; event konfliknya sendiri tidak dicegah. Celah nyata: tidak
ada penjaga apa pun yang mencegah instance kedua ikut polling token yang sama — container kedua,
proses host manual, atau `docker compose up` di salinan repo lama. Instance kedua tidak gagal
berisik; ia mencuri separuh update dari yang pertama dan tidak ada operator yang bisa tahu sebabnya.

Mekanisme: abstract AF_UNIX socket `voldemort-menu-bot-getupdates` sebagai mutex host-wide. Dipilih
karena hidup di network namespace yang container ini bagi dengan host (`network_mode: host`), tidak
butuh file dan tidak butuh cleanup, dan kernel melepasnya begitu pemegangnya mati — apa pun cara
matinya, jadi tidak ada lock basi yang bisa mengunci restart. Dipasang di `run_bot()` sebelum
`build_application()`, jadi instance kedua tidak pernah sampai ke `run_polling()`. Kalau slot sudah
dipegang: log error berisi perintah diagnosis, lalu exit 1; dengan `restart: unless-stopped` ia jadi
standby yang otomatis mengambil alih bila pemegang slot mati.

**Sisa celah yang disengaja**, didokumentasikan di docstring: duplikat yang berjalan di network
namespace sendiri (container bridged biasa, atau mesin lain) tidak terlihat guard. Kasus itu ditangani
lapis deteksi — threshold 3/120s → paging `Persistent getUpdates Conflict` sekali per 300s cooldown.

`tests/test_singleton_guard.py` → `PASS: 4 checks` (klaim pertama sukses, klaim kedua exit 1, slot
dilepas saat holder menutup, klaim ulang di satu proses idempotent).

### [11:45] Bug: `journal-alert.sh` berteriak FAILED pada unit yang sehat

User menerima page `🚨 hermes-journal.service FAILED` yang badan pesannya sendiri berbunyi
`result/status/state: inactive success 0`. Page itu **kiriman saya sendiri** — verifikasi manual jalur
backstop pukul 11:11 WIB — dan saya tidak memberinya label uji, padahal page lewat bot Hermes saya
labeli `🧪 TES`. Kelalaian itu justru menyingkap bug nyata.

**Root cause**: header di-hardcode `🚨 <unit> FAILED` dan skrip tidak pernah memeriksa `Result`. Dua
hipotesis lain dibuang dengan bukti: systemd tidak pernah memicu `OnFailure` (tidak ada di journal,
transisi terakhir `Finished ... success`), dan unit tidak pernah gagal lalu di-reset
(`Result=success`, `ExecMainStatus=0`).

Yang lebih berbahaya daripada kata yang salah: skrip `OnFailure` yang tidak bisa membedakan gagal dari
sukses melatih pembacanya mengabaikannya, tepat pada satu alert yang benar-benar penting.

**Loop**: `--dry-run` ditambahkan lebih dulu sebagai instrumentasi (mencetak pesan alih-alih
mengirimnya), sehingga bug bisa diuji tanpa menaruh pesan menakutkan di DM. Loop mereproduksi gejala
yang ditempel user persis, deterministik, <1 detik.

**Fix diuji dua arah**, karena membungkam positif palsu hanya separuh pekerjaan:

| Arah | Sebelum | Sesudah |
|---|---|---|
| Unit sukses | `🚨 ... FAILED` | `ℹ️ ... did NOT fail (Result=success)` + menyebut pemanggilan manual sebagai sumber |
| Unit benar-benar gagal | `🚨 ... FAILED` | `🚨 ... FAILED` (tetap) |

Arah kedua dibuktikan terhadap unit throwaway yang sengaja `ExecStart=/bin/false`, lalu unit itu
dibersihkan (`reset-failed` + hapus + `daemon-reload`; nol unit failed tersisa).

**Batas yang jujur**: yang terverifikasi adalah perilaku skripnya. Bahwa systemd benar-benar
*memanggil* skrip saat unit gagal hanya dikonfirmasi dari konfigurasi
(`systemctl show -p OnFailure` → `hermes-journal-alert.service`), bukan dari kejadian nyata —
membuktikannya berarti sengaja menggagalkan tick jurnal.

Karena skrip ini symlink dari vault, perbaikannya langsung live tanpa langkah deploy.

**Tick otonom malam ini**: belum jalan. Timer elapse 16:50 UTC / 23:50 WIB, 12 jam dari saat diagnosis.
Entri `Hermes/Journal/2026-09-26.md` yang sudah ada berasal dari tick manual penerimaan.

## 🔐 Sisa terbuka — rotasi kredensial, butuh tindakan manual

Tidak ada API yang bisa dipakai dari box ini: token bot hanya bisa dicabut lewat BotFather (interaksi
manusia di Telegram), dan merotasi token Cloudflare butuh kredensial ber-permission "API Tokens Write"

**Kenapa wajib, bukan sekadar kehati-hatian**: tiga nilai ini terekspos ke transcript sesi AI hari
ini, dua di antaranya karena kesalahan saya sendiri — `CF_R2_TOKEN` + `CF_API_TOKEN` lewat
`docker inspect` dengan grep terlalu lebar, dan `BOT_TOKEN` lewat fallback `sudo -n cat` yang berjalan
sebelum filter nama-key. Pelajaran: saat membandingkan file `.env`, ekstrak **nama key** saja
(`grep -oE "^[A-Za-z_]+="`), jangan pernah `cat` isinya.

Langkah, endpoint diambil dari kode bukan dari ingatan:

1. **`BOT_TOKEN`** — @BotFather → `/mybots` → @voldemort_menu_bot → API Token → Revoke. Bot id tetap
   `8874533491`, hanya bagian secret berubah. Begitu di-revoke, semua salinan lama mati seketika —
   inilah satu-satunya perbaikan sesungguhnya atas kebocoran.
2. **`CF_API_TOKEN`** — dipakai `services/cloudflare_flux.py:72` →
   `POST /client/v4/accounts/{id}/ai/run/@cf/black-forest-labs/flux-1-schnell`. Roll di My Profile →

   Tokens, scope Workers R2 Storage (Edit, karena ada PUT object).
